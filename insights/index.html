LLM tool calling in production 4

What breaks when open-weight models call tools in production, and how to test for it.

  1. Catalog metadata is not a health check A provider catalog listed our model as healthy with function calling while every real call failed, and a typo passed lint. Only a live probe tells the truth. →
  2. The 400 that only happens on the tool-result turn A model handled a single tool call but returned HTTP 400 when we sent the tool result back, and looked fast because it failed fast. Test the continuation. →
  3. The eval that scored 100% with zero tool calls A tool-calling benchmark reported a perfect score for a model that failed every request. An empty-denominator bug, and how to gate model selection properly. →
  4. Our fallback hid an outage for weeks A cheap model failed every request, a fallback to a stronger model kept users happy, and only an unrelated code path noticed. What to monitor and how to test. →

Evaluating models 6

Qualifying models and building evals and tests you can trust.

  1. Testing tool calling on Hugging Face Inference Providers A method for qualifying tool calling across Hugging Face Inference Providers: the endpoint, provider pinning, fixture design and the traps. No measured results. →
  2. A stub LLM that always returns clean JSON hides your parsing bug Our tests passed because the stub returned tidy JSON and the check only looked at the status code. Real models add fences and prose. Test the dirty case. →
  3. Record and replay for LLM tests Record against live APIs once, replay in CI for fast, cheap, deterministic tests. Plus a static test that stops placeholder values reaching the model as facts. →
  4. Using an independent LLM judge, and its limits A method note on LLM-as-judge: keep the judge independent, keep samples honest, treat a past production answer as a baseline and not as truth. →
  5. Grade the tool call, not the text Our first benchmark run scored zero for every model because the grader read message text while the answer was in tool-call arguments. How to grade it right. →
  6. How to qualify an LLM router model: hard gates before cost Sorting candidate models by price first surfaces broken ones. Disqualify on failures, then rank on cost and latency. The gates, the process and the traps. →

Agent design patterns 5

General patterns for agent loops, tools and tiered models.

  1. MCP servers versus an internal tool bridge What an MCP server can replace between an agent and your app, what we kept on an internal bridge and why, and a safe way to migrate one tool category at a time. →
  2. Which tools do you show the model? Sending every tool definition costs prompt tokens on each call. Showing a subset saves them, but keyword routers and selector models each have blind spots. →
  3. Cheap router model plus stronger fallback: design and blind spots A tiered LLM setup saves money until the fallback hides failures or quietly spends more. Design rules for tiers, and the blind spots that break them. →
  4. Confirmation-gated write tools and idempotency Pause agent write actions for user approval and make retries safe: race conditions, declined and expired approvals, and idempotency keys against double writes. →
  5. A bounded agent loop that fails safely Iteration caps, typed tool errors, a final tool-less summary step and cost budgets that fail closed: stop an agent loop from running away or leaking output. →

LLM operations 4

Cost tracking, alerting and monitoring for LLM features.

  1. Built but never wired: monitoring that had no callers Our quality scoring and request logging were finished and read by dashboards, but no production code called them. How an audit found it and what to test. →
  2. Your anomaly detector is relative, so it misses slow ramps Baseline-relative cost alerts stay quiet when spend climbs slowly, and they can be noisy at low volume. Add absolute limits, floors and a provider health check. →
  3. Cache-aware LLM cost accounting Cached-token discounts are easy to model wrong. The tolerant parsing, the zero-default trap and the tests that keep per-call LLM cost honest. →

Output guardrails 5

Validating, containing and caching what models return.

  1. Principles for caching LLM responses What belongs in an LLM cache key, what must never be shared across users, and which results must not be cached at all. General principles from real near-misses. →
  2. Refusals that return HTTP 200 A model that refuses or has nothing to analyze still returns success. Treat a refusal as its own outcome, retry once, and keep it out of accuracy stats. →
  3. Detecting degenerate model output Repetition loops and garbled text can burn tokens and reach users. Detect them mid-stream, cancel, retry once at lower temperature, then degrade gracefully. →
  4. Drop, don't error: sanity checks on model output When one field of a model's answer is out of range, discard that field and count it, instead of failing the whole request. How, and when not to clamp. →
  5. Structured output with an abstain option Models over-commit to an answer when the right response is insufficient data. Make abstain a first-class value with a required reason, and route it to a human. →
