LLM tool calling in production 5

What breaks when open-weight models call tools in production, and how to test for it.

  1. The model answered. We threw the answer away. A model gave complete, valid answers and our system discarded them as errors. How we found it, how we fixed it safely, and the bug we found in our own fix. →
  2. Catalog metadata is not a health check A provider catalog listed our model as healthy with function calling while every real call failed, and a typo passed lint. Only a live probe tells the truth. →
  3. The 400 that only happens on the tool-result turn A model handled a single tool call but returned HTTP 400 when we sent the tool result back, and looked fast because it failed fast. Test the continuation. →
  4. The eval that scored 100% with zero tool calls A tool-calling benchmark reported a perfect score for a model that failed every request. An empty-denominator bug, and how to gate model selection properly. →
  5. Our fallback hid an outage for weeks A cheap model failed every request, a fallback to a stronger model kept users happy, and only an unrelated code path noticed. What to monitor and how to test. →

Qualifying models and building evals and tests you can trust.

  2. Half our replay sample tested the wrong prompt We rebuilt production requests for a model eval and paired nearly half with answers to a different prompt. How it showed, what we withdrew, and the guards. →
  3. What broke when we tested 20+ models on one tool call We ran more than twenty models through one structured-decision task with a forced tool call. About half failed on liveness. The failure types, and what passed. →
  4. Recording the bad day: replay tapes for rate limits and retries Our record and replay setup could not hold a 429 followed by a 200. What a sequence recorder needs, and how to capture failures no host gives on demand. →

  6. A stub LLM that always returns clean JSON hides your parsing bug Our tests passed because the stub returned tidy JSON and the check only looked at the status code. Real models add fences and prose. Test the dirty case. →

  8. Using an independent LLM judge, and its limits A method note on LLM-as-judge: keep the judge independent, keep samples honest, treat a past production answer as a baseline and not as truth. →

Output guardrails 5

Validating, containing and caching what models return.

  1. Principles for caching LLM responses What belongs in an LLM cache key, what must never be shared across users, and which results must not be cached at all. General principles from real near-misses. →
  2. Refusals that return HTTP 200 A model that refuses or has nothing to analyze still returns success. Treat a refusal as its own outcome, retry once, and keep it out of accuracy stats. →
  3. Detecting degenerate model output Repetition loops and garbled text can burn tokens and reach users. Detect them mid-stream, cancel, retry once at lower temperature, then degrade gracefully. →
  4. Drop, don't error: sanity checks on model output When one field of a model's answer is out of range, discard that field and count it, instead of failing the whole request. How, and when not to clamp. →
  5. Structured output with an abstain option Models over-commit to an answer when the right response is insufficient data. Make abstain a first-class value with a required reason, and route it to a human. →
